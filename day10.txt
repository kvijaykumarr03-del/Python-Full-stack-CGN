1. Data Redundancy
•    Data redundancy means having the same data stored at multiple places within a database.
•    Data redundancy leads to anomalies (errors) in the database.
•    It becomes very hard to maintain a database that has redundant data.
Example — Data Redundancy:

Notice that the row for "SAI, 21, A" is repeated — this duplication is an example of data redundancy.
2. Types of Anomalies
Data redundancy causes anomalies. The three types of anomalies are:
•    Insertion Anomalies — difficulty inserting data due to missing/dependent information.
•    Updation Anomalies — the need to update the same data in multiple places, risking inconsistency if missed.
•    Deletion Anomalies — deleting a record unintentionally removes other, unrelated information stored in the same row.
3. What is Normalization?
Normalization is the process of organizing data in a database to reduce data redundancy and improve data integrity.
It involves dividing large tables into smaller ones and defining relationships between them to ensure data consistency.
The main goals of normalization are:
•    Eliminate data redundancy (duplicate data).
•    Ensure data dependencies are logical.
•    Improve data integrity (missing values) and consistency (correctness).
4. Normalization Forms — Overview
Normalization is typically carried out through a series of normal forms (NF), each addressing specific issues:
•    First Normal Form (1NF) — Eliminate repeating groups.
•    Second Normal Form (2NF) — Eliminate partial dependency.
•    Third Normal Form (3NF) — Eliminate transitive dependency.
•    Boyce-Codd Normal Form (BCNF) — A stricter version of 3NF.
•    Fourth Normal Form (4NF) — Handle multi-valued dependencies.
•    Fifth Normal Form (5NF) — Handle join dependencies.
5. First Normal Form (1NF)

•    It states that an attribute of a table cannot hold multiple values.

Now we identify the primary key.
A student can attend multiple courses.
ALTER TABLE student_course_1nf ADD PRIMARY KEY (student_id, course);

Step 3: Convert 2NF to 3NF
Now look at the enrollment_2nf table:
student_id
course
trainer
trainer_phone


We can identify another dependency:
trainer → trainer_phone

For example:
Kumar → 9876543210
Ramesh → 9876543211
Suresh → 9876543212
But:
student_id + course → trainer
trainer → trainer_phone
Therefore:
student_id + course → trainer → trainer_phone
This is a transitive dependency.
To achieve 3NF, we remove this dependency.

Create TRAINER table
CREATE TABLE trainer_3nf (
    trainer_id INT PRIMARY KEY,
    trainer_name VARCHAR(50),
    trainer_phone VARCHAR(15)
);
Insert:
INSERT INTO trainer_3nf
VALUES
(1, 'Kumar', '9876543210'),
(2, 'Ramesh', '9876543211'),
(3, 'Suresh', '9876543212');

Create COURSE table
CREATE TABLE course_3nf (
    course_id INT PRIMARY KEY,
    course_name VARCHAR(30),
    trainer_id INT,
    FOREIGN KEY (trainer_id) REFERENCES trainer_3nf(trainer_id)
);
Insert:
INSERT INTO course_3nf
VALUES
(1, 'Java', 1),
(2, 'Python', 2),
(3, 'SQL', 3);

Create ENROLLMENT table
Now instead of storing trainer details here, we store IDs.
CREATE TABLE enrollment_3nf (
    student_id INT,
    course_id INT,
    PRIMARY KEY (student_id, course_id),
    FOREIGN KEY (student_id) REFERENCES student_2nf(student_id),
    FOREIGN KEY (course_id) REFERENCES course_3nf(course_id)
);
Insert:
INSERT INTO enrollment_3nf
VALUES
(101, 1),
(101, 2),
(102, 2),
(102, 3),
(103, 1),
(103, 3);

1. The Entity-Relationship (ER) Model
The Entity-Relationship (ER) Model is a conceptual framework used to describe data relationships in a structured way.
Components of the ER Model:
•    Entities
•    Attributes
•    Relationships
•    Cardinality
2. Entity
An entity represents a real-world object or concept that has a unique existence.
Entities are classified into:
•    Strong Entities — exist independently (e.g., Customer, Student, Book).
•    Weak Entities — depend on other entities for existence (e.g., Order_Item depends on Order).

Diagram: Strong Entity vs. Weak Entity (Slide 3)
3. Attributes
Attributes describe properties or characteristics of an entity.
Types of Attributes:
•    Simple (Atomic) Attributes — cannot be divided further (e.g., Name, Age).

Diagram: Simple (Atomic) Attribute (Slide 4)
•    Composite Attribute — can be broken down into sub-attributes (e.g., Address → Street, City, Zip).

Diagram: Composite Attribute (Slide 5)
•    Key Attribute — uniquely identifies an entity (Primary Key).
•    Multivalued Attributes — can have multiple values (e.g., Phone Numbers).
•    Derived Attributes — calculated from other attributes (e.g., Age from Date of Birth).

Diagram: Key, Multivalued, and Derived Attributes (Slide 6)

5. Relationships
A relationship represents an association between two or more entities.
Types of Relationships:
•    One-to-One (1:1)
•    One-to-Many (1:M)
•    Many-to-Many (M:N)
6. One-to-One (1:1) Relationship
One-to-One (1:1) → Each entity in A is related to one entity in B.
Example: COUNTRY – PRESIDENT.

Diagram: One-to-One Relationship — Country and President (Slide 9)
7. One-to-Many (1:M) Relationship
One-to-Many (1:M) → One entity in A can relate to multiple entities in B.
Example: TEACHER – STUDENTS.

Diagram: One-to-Many Relationship — Teacher and Students (Slide 10)
8. Many-to-Many (M:N) Relationship
Many-to-Many (M:N) → Multiple entities in A relate to multiple entities in B.
Example: STUDENTS – COURSES.

Diagram: Many-to-Many Relationship — Students and Courses (Slide 11)
9. Cardinality
Cardinality defines the number of instances of an entity involved in a relationship.
Types:
•    1:1 (One-to-One)
•    1:M (One-to-Many)
•    M:N (Many-to-Many)
